## 使用者確認的方向

Winfinder 提供不同的視覺介面；Windows 上的檔案操作與互動以同機 Windows 檔案總管為基準。Windows 有公開 Shell 介面時優先整合，避免以自訂邏輯重做核心檔案行為。欄式檢視、深色玻璃介面等既有視覺特色保留。

滑鼠與鍵盤事件仍需由 Winfinder 接收、轉換及維護選取和焦點；呼叫 Shell 並不會自動獲得完整的 Explorer 互動。驗收必須同時覆蓋介面行為與系統執行結果。

## 邊界與方案

沿用 renderer → Tauri 指令 → Windows Shell 的邊界。介面負責焦點、選取、導覽與顯示；Windows 介接層負責原生操作、對話框與完成結果；系統剪貼簿與檔案系統仍是跨應用的資料來源。

比較兩個方向：

| 方案 | 優點 | 代價 |
| --- | --- | --- |
| 保留自訂執行、逐項模仿 Explorer | 改動較少，跨平台共用較多 | 權限、衝突、復原與 Shell 擴充需持續自行維護，不符合已確認方向。 |
| 沿用外觀，Windows 執行路徑接 Shell | 符合使用者方向，沿用系統能力 | 需重新整理非同步結果、取消、部分成功與復原；互動仍需逐項實作及驗證。 |

採第二方向。這是使用者確認的產品方向；具體 API、結果契約與生命週期在各切片實作前確認，不將本計畫當作已核准的詳細設計。

## 分段順序與驗收

1. **PPT 原生預覽**：先取得同一檔案在 Explorer 可預覽、Winfinder 失敗的重現證據。記錄 handler 選擇、建立、初始化、SetWindow、DoPreview、逾時等階段的錯誤；避免記錄文件內容。修正需有先失敗的回歸證據。使用實際 Office handler 驗證版面、圖形、切檔、縮放及關閉；只有文字擷取或 RTF handler 成功不算 PPT 通過。
2. **檔案核心操作**：Windows 複製／搬移與重新命名逐條改接原生執行，處理進度、取消、部分完成、名稱衝突、檔案占用、權限與復原。僅依實際成功結果更新介面；取消或結果不明時不得自動重試可能已執行的寫入。
3. **互動對齊**：建立同機 Explorer 對照案例，逐項驗證單擊／雙擊／右鍵、Shift／Ctrl 多選、方向鍵、F2、Delete／Shift+Delete、Ctrl+C/X/V/Z、拖曳修飾鍵與前後導覽。依檢視模式確認空間選取規則，避免破壞欄式檢視特色。

每段通過實際驗證後才進下一段；不能用元件測試取代真實系統處理程式驗證。無法當場驗證的項目標示 MANUAL_VERIFY_REQUIRED，附原因。第三方擴充與 Office 版本差異另列環境，不宣稱通用通過。

## 風險及控制

- 原生操作的部分成功可能與既有自訂復原紀錄不同；先定義結果與復原歸屬，避免雙重執行。
- 系統處理程式載入緩慢或失敗不得卡住主介面；保留請求失效、逾時與宿主隔離，診斷錯誤可追蹤。
- 不把缺少系統預覽處理程式當作 Winfinder 已正常預覽；替代內容須明確標示。
- 公開 Shell API 不涵蓋所有 Explorer 內部能力；遇到限制記錄差異及實測結果，不自行假定完全等同。
- 目前無既有 PRD／SRS／SDD／RTM ID 可做下游追溯；本次只建立異動計畫與專案規則，後續新增 ID 時須補相應追溯與驗證。
